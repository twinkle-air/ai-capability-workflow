# AI Skill / Agent 开发工作流

仅在用户要求**开发、修改、测试或维护 AI Skill / Agent** 时使用。普通编程、写作、资料检索、产品咨询等任务不调用本工作流；只有任务明确以 Skill / Agent 成品或其维护为目标，才进入以下流程。

本工作流按以下五个阶段执行。用户确认任务清单是构建前的硬关口；没有明确确认，就停在第一阶段。用户可修改清单，修改后提交新版再次确认。不能将沉默、超时或泛泛的“继续”推定为对未展示清单的确认。

## 1. 研究需求并提交任务清单

先从用户原话提取目标、使用者、输入、输出、目标平台、约束与未知项。检索与任务相关的论文、标准、官方文档和原始资料；涉及具体平台时核对其当前官方规范。按主题扩展同义词、相邻方案和反例，记录检索范围、日期、来源及未覆盖处。尽量覆盖影响方案选择的关键证据，不声称穷尽所有文献。

优先采纳原始论文、正式标准、官方技术文档、官方数据和可核验的一手案例。核对作者/机构、发布日期或版本、方法与适用范围；区分论文结论、工程经验、推断与假设。重要或有争议的结论尽量交叉核对。对来源不明、无法追溯、与原始材料冲突或超出证据适用范围的数据，标记为“不采用”，不得进入实现依据。使用 [references/research.md](references/research.md) 记录来源和取舍。

结合可靠证据丰富需求，写一份**详细、可逐项验收的任务清单**：需求澄清、交付形态、功能与边界、资料依据、实现任务、样本与测试、验收标准、交付物。每项写编号、具体动作、完成证据；区分用户原始要求与研究后建议，不擅自扩大范围。将清单和关键来源交给用户确认，明确说明可修改。**在用户确认当前版本前，不进入构建、样本执行测试或最终交付。**

## 2. 按确认清单构建

以确认的清单为实施边界。Skill 的结构要点见 [references/skill.md](references/skill.md)，Agent 见 [references/agent.md](references/agent.md)。只把有可靠依据、可说明适用条件的数据写进成品；无法核实的内容不采用，并记录对功能的影响。实现中发现清单需改变范围、关键功能或验收标准时，先提交变更清单并取得确认，再执行变更。

按目标平台生成可用的源文件、配置、资源及必要脚本。代码/程序交付在提交前必须编译或执行对应的语法、类型、静态检查，并记录结果。不得用结构校验替代行为测试。

## 3. 制作或获取样本并测试

按确认清单创建样本，或从允许使用的来源下载样本；记录来源、版本、许可/使用条件、获取日期和必要的脱敏处理。样本应能代表目标任务，至少覆盖正常输入，并按风险补充边界、失败或权限场景。合成样本须明确标记，不能冒充真实案例。

将样本实际投入成品运行，记录输入、环境、预期、实际输出及证据。发现问题立即定位并修复，然后重跑失败场景和受影响的正常场景；循环到约定验收标准通过。若样本不可获得、测试环境不可用或缺陷无法解决，不得声称“测试通过”，应说明阻碍并与用户商定清单变更或后续处理。

## 4. 对照清单复核

样本测试通过后，逐项核对已确认清单，将每项标为“完成 / 未完成 / 不适用”，附文件或测试证据。未完成项不得暗中略过；有范围变更时须先取得用户对新版清单的确认。只有所有必需项完成且关键测试通过，才进入提交。

## 5. 交付可复用成品

交付源文件、可使用的 Skill / Agent、安装与使用说明、来源记录、样本测试记录和清单复核结果。说明适用环境、依赖、输入输出、权限、已验证范围、已知限制与维护方式。移除临时文件、密钥和私人数据；样本如受许可或隐私限制，交付可复现的获取方法或脱敏替代样本。

## 配套模板

本技能包的 [templates](templates) 提供项目简报、来源记录、任务清单、验证记录和交付说明。安装到其他位置后，仍从技能包内读取这些文件；不得依赖原仓库路径。根据实际项目填写；空白模板不是已完成的证据。目标 harness 的加载方式见 [references/harnesses.md](references/harnesses.md)，仅在安装或排查时读取。
