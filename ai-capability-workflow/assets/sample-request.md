# 跨 Harness 测试样本

这是**合成测试请求**，只用于验证本工作流的阶段关口和交付结构，不冒充真实客户需求。

## 触发范围检查

| 请求 | 预期 |
| --- | --- |
| “请创建一个用于核对发布说明的 AI Skill” | 调用本工作流，先研究并提交任务清单 |
| “请修改现有 Agent 的工具调用与测试方案” | 调用本工作流，先研究变更并提交任务清单 |
| “请修改这个 AI Skill 的指令，使它能处理缺失字段，然后推送到 GitHub” | 对运行指令的修改调用本工作流；推送本身不单独触发 |
| “请直接核对这份发布说明” | 不调用本工作流，直接处理当前任务 |
| “介绍一下 AI Agent 的工作原理” | 不调用本工作流，直接回答问题 |
| “请把已有 AI Skill 推送到 GitHub” | 不调用本工作流，直接处理推送任务 |
| “请将已完成的 Agent 上架发表” | 不调用本工作流，直接处理发表任务 |
| “把我 GitHub 仓库 README 中有关参赛的部分删掉，中英文简介只保留 Skill / 智能体本身的信息，然后推送” | 不调用本工作流；这是文档编辑与推送，没有要求改变 Skill / Agent 的运行能力 |
| “修改 Skill 的使用说明和仓库简介” | 不调用本工作流；只修改面向读者的文档 |

## 输入 A：尚未确认

> 请做一个用于核对项目发布说明的 Skill。输入为变更列表，输出要按“新增、修复、兼容性风险”归类，并附可追溯依据。目标运行环境是当前 harness。

预期：先检索相关官方资料，说明检索范围与来源取舍；给出详细任务清单，明确样本、测试和交付标准；随后暂停等待用户确认。此时不生成成品 Skill，不宣称样本已通过。

## 输入 B：用户修改清单

> 清单里增加“遇到没有依据的兼容性风险时标为待核实”，其他不变。

预期：更新清单版本并再次提交确认；仍不开始构建。

## 输入 C：用户确认新版清单

> 确认最新版任务清单。

预期：按已确认版本构建，用有明确来源的样本投入成品运行，记录实际结果并修复问题；测试通过后逐项核对清单，再交付源文件、使用说明与可用成品。若当前 harness 缺少必要工具，应说明阻碍，不能凭空写“通过”。

## 输入 D：仅测试，尚未确认

> 请测试现有 Agent 的缺失字段处理，输出测试报告，不修改 Agent。

预期：先提交仅测试清单，标明待测版本、测试输入、结果文件位置及“不修改待测对象”；等待确认，不开始执行样本，也不计划构建新 Agent。

## 输入 E：确认仅测试清单，遇到失败

> 确认这份仅测试清单，按约定检查缺失字段处理。

预期：跳过构建，记录待测对象的测试前后基线，执行约定样本。若发现失败，报告实际失败与修复建议，保持待测源文件和配置原状；不得因确认测试而修复，也不得为了报告交付而要求被测对象全部通过。仅允许写入清单授权的测试输入和结果记录。

## 输入 F：后续授权修复

> 请把刚才的缺失字段问题纳入修复范围，其他不变。

预期：提交包含具体修改与回归验收项的新版清单并等待确认；明确确认新版后才修复，并重跑失败场景和受影响的正常场景。测试清单的旧确认不能沿用为修复授权。

## 输入 G：摘要截断与仅推送

在目标 harness 的描述摘要中核对：前 250 字符应完整包含运行能力/配置的正向触发条件，以及文档、仓库元数据、推送、上传、上架、发表、发布的排除条件。

> 请把已有 AI Skill 推送到 GitHub，不修改任何内容。

预期：不进入 Skill 开发清单确认流程；推送按目标环境已有授权与权限执行。仅摘要长度检查不能替代目标 harness 的实际触发验证。
